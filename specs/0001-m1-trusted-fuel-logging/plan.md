This plan names the components, the contracts between them, the build order, and
the risks. It does not contain code. FR and INV references point at `spec.md`
and `data-model.md`.

## 1. Approach

Build one `packages/api` service. Drive every capability from the HTTP API.
Keep two machine-readable sources of truth — the Zod route schemas and the
Drizzle table schema — and generate everything else. CI blocks any drift
(`specs/README.md` gate list).

Build in vertical slices in the order in section 12, each slice ending green on
the full CI pipeline.

### Plan decisions to confirm in review

- `openid-client` v6 as the OIDC RP library.
- `@node-rs/argon2` over `argon2` (node-gyp).
- `postgres.js` over `pg`.
- Tests hit the app in-process via `app.request()`, plus one real-socket journey
  suite. No Playwright in M1 (no UI).
- Rate-limit store is in-memory for M1; a shared store waits for a real
  multi-process deployment (R-1).

## 3. Request flow

```
HTTP request
  -> request-id + structured log middleware
  -> rate-limit middleware        (sign-in, reset, invite accept; FR-2.6)
  -> auth middleware              (session cookie or bearer; sets ctx.user; FR-2.2)
  -> must-change-password gate    (403 password_change_required except change-pw; FR-4.5)
  -> admin gate                   (admin routes only; FR-8/9/10; constitution principle 8)
  -> zod-openapi route handler    (validates request, shapes response)
  -> domain service               (typed, no HTTP, no SQL dialect)
  -> persistence contract         (interface in domain/, implemented in db/repositories/)
  -> Drizzle adapter              (postgres or sqlite)
  -> database
```

The domain layer never imports Hono or a Drizzle dialect. Routes never build
SQL. This keeps FR-15 conversion, FR-13 invariants, and INV-9 isolation in one
place each and testable without a server.

## 4. Persistence contract and adapters

### The contract

`domain/ports.ts` declares interfaces the services depend on, for example
`UserRepo`, `VehicleRepo`, `FuelEntryRepo`, `TokenRepo`, `SessionRepo`,
`AuditRepo`, `SettingsRepo`, plus a `UnitOfWork` that runs a callback inside one
transaction and exposes row locks.

Services receive repos through a small container. Tests pass either a real
adapter or an in-memory fake.

### Dual-dialect Drizzle

`db/schema/` defines each table twice through thin helpers that pick column
builders by dialect (`data-model.md` adapter notes): `uuid` vs `text`,
`timestamptz` vs ISO `text`, `jsonb` vs `text`, `text[]` vs JSON `text`,
`boolean` mapping, `lower(email)` unique vs `COLLATE NOCASE`. One inferred row
type per table is exported for the domain layer.

`db/adapters/postgres.ts` and `sqlite.ts` build a Drizzle client and expose the
same `UnitOfWork`. The adapter is chosen from the `DATABASE_URL` scheme
(`env.ts`).

### Locking for INV-2 and INV-6

- INV-2 (odometer progression). `FuelEntryRepo.createOrUpdate` runs inside
  `UnitOfWork`, first `SELECT ... FOR UPDATE` on the `vehicle` row (Postgres),
  or a `BEGIN IMMEDIATE` write transaction (SQLite), then reads the two
  neighbours in `(entry_date, created_at)` order and checks both. FR-13.3,
  FR-13.7.
- INV-6 (last active admin). Role, status, and delete changes on `user` run
  inside `UnitOfWork` after locking the `deployment_settings` singleton row,
  then count active admins, then apply. FR-8.8, FR-13.7.
- Per-row checks (non-negative, positive volume, enum membership, foreign keys,
  `fuel_volume_precision between 1 and 3`, single-row guards) are database
  `CHECK` constraints and indexes, generated from the schema.

## 5. Units

`units/` holds pure functions. Canonical integers only cross the persistence
boundary (D-1): `odometer_mi_e3`, `volume_gal_e3`, `total_cost_usd_cents`.

- `toCanonical(value, unitSystem, quantity)` and `fromCanonical(...)`.
- `imperial` input is a direct scale. `metric` input converts km→mi, L→gal, then
  scales. FR-15.2.
- `roundVolume(value, precision)` and `formatPrice(...)` apply
  `deployment_settings.fuel_volume_precision` (FR-15.6). Storage stays scale 3;
  the setting only bounds accepted and displayed digits.
- The route response builder attaches both the canonical integers and a display
  projection (FR-15.3). A property test asserts the round trip is stable to the
  configured precision (FR-15.4).

## 6. Validation and invariants — where each lives

| Rule | Enforced by |
|---|---|
| positive volume, non-negative cost and odometer, enum membership, FK, precision range, single-row guards | DB `CHECK` / FK / unique index (generated) |
| INV-2 odometer progression, both neighbours | `FuelEntryRepo` inside `UnitOfWork` with a vehicle row lock |
| INV-3 archived vehicle read-only for entries | `FuelEntry` service |
| INV-4 future-date <= 2 days in user tz | `FuelEntry` service (needs `user.time_zone`) |
| INV-6 last active admin | `User` service inside `UnitOfWork` with the settings row lock |
| INV-7 email uniqueness | `lower(email)` unique index + friendly error mapping |
| INV-8 identity uniqueness | `(provider_key, subject)` unique index |
| INV-9 per-user isolation | every repo method takes `userId`; queries join through `vehicle`; a lint check forbids a `fuel_entry` query without a user scope |

## 7. Bootstrap and schema lifecycle

`bin/chotu.ts` exposes `bootstrap`, `token issue`, `token revoke`.

`bootstrap` (FR-1):
1. Connect with `DATABASE_BOOTSTRAP_URL`. Probe privileges with a dry
   `CREATE`/`DROP` in a savepoint. Missing grant -> exit with the named grant
   (FR-1.4).
2. Apply `drizzle-kit` migrations. Write `schema_meta` (version, build,
   applied_at). A version the build cannot handle -> exit (FR-1.3).
3. Create the `deployment_settings` singleton from flags or defaults
   (`invite_only`, `imperial`, `USD`, `America/New_York`,
   `fuel_volume_precision=3`).
4. Create the first admin: `--admin-email`/`--admin-password`, or print a
   one-time set-password link, or seed `scott@chotu.local` / `tiger` with
   `must_change_password` and a printed warning (FR-1.5).
5. Issue one API token for that admin, print once (FR-1.7).

Startup: `env.ts` decides mode from `CHOTU_ENV`. In `production`, if any admin
still holds an unchanged seeded default password, refuse to start and say why
(FR-1.6, AC-12). In `production`, refuse a SQLite `DATABASE_URL` (FR-1.10).

The runtime uses `DATABASE_URL` with the low-privilege role (FR-1.9): DML on
Chotu tables, `INSERT` only on `audit_log`, no DDL.

## 8. Auth

### Sessions (FR-2)
Opaque 256-bit id, stored as SHA-256 in `session`. Sent as an `HttpOnly Secure
SameSite=Lax` cookie and echoed in the sign-in response body for headless
clients (Q-11, constitution). Sign-out and reset revoke. TTL from settings.

### API tokens (FR-5)
`cht_` prefix + 256-bit random, shown once, stored as SHA-256 in `api_token`
with `user_id` and `label`. Several active per user (Q-8 = A). Optional expiry
from `api_token_ttl_seconds`. Auth middleware accepts `Authorization: Bearer`
for both a session credential and a token; it resolves which by prefix.

### Passwords (FR-4)
`@node-rs/argon2` Argon2id, parameters fixed in `auth/password.ts`. Reset and
invite tokens: 256-bit random, SHA-256 at rest, short TTL, single use.
`must_change_password` gate is middleware (FR-4.5). Change-password accepts a
session or a token so the seeded admin can clear it (FR-4.1).

### OIDC (FR-6)
`openid-client` RP. Per provider: discovery from `issuer_url`, Authorization
Code + PKCE. Routes: `GET /auth/oidc/:key/start` and `GET /auth/oidc/:key/callback`
(both in the FR-2.2 unauth list). On callback: validate, match or create
`identity` by `(provider_key, sub)`, enforce `allowed_email_domains` /
`allowed_groups`, auto-provision when enabled and policy is `sso_auto`, then
start a session. Client secret is write-only over the API; stored per R-3
(encrypted-at-rest or env reference — plan default: env reference, DB-encrypted
optional). Tests run against a mock issuer in `test/support` (AC-11, `oidc`
fixture). The Device Authorization Grant is M1.5, not here.

### Rate limiting (FR-2.6, NFR)
Token-bucket middleware on sign-in, reset request, invite accept. Keyed per IP
and per account. Draft limits from the spec NFR, read from config so they can be
tuned. `429` + `Retry-After`.

## 9. Reconciliation

`reconcile/` holds a registry of checks, each `(scope) => Finding[]`:
`duplicate`, `orphaned`, `odometer-tie`, `odometer-decrease`, `missing-field`,
`out-of-range` (FR-17.3). A per-user run scopes to one user (FR-17.1). The
deployment run iterates users and returns `{recordId, userId, checkCode,
message}` with no field values (FR-17.2, INV-9). Read-only.

## 10. Export

`export/` builds one JSON document: `{schemaVersion, canonicalUnits,
fuelVolumePrecision, exportedAt, profile, vehicles[], fuelEntries[]}` (FR-16,
Q-6 = A). Per-user for a user; all tables for an admin backup (FR-18.1) with
secrets excluded. No import in M1.

## 11. OpenAPI pipeline

`contract/build.ts` assembles the document from the `@hono/zod-openapi`
registry. `pnpm openapi:write` writes `openapi.yaml`. The API serves the same
document at `GET /openapi.yaml` and a health doc at `GET /healthz` (FR-19.1,
FR-19.4), both unauthenticated. CI regenerates and runs `git diff --exit-code`
(gate 3, FR-19.2). Every route carries request, response, `security`, and error
codes, with prose aimed at an LLM caller (FR-19.3).

## 12. Error model

One body: `{ code, message, details? }`. `code` values live in
`domain/errors.ts` as a closed union and are listed in every route's OpenAPI
responses. HTTP mapping: validation `400`, auth `401`, forbidden / wrong-owner
surfaces as `404` for vehicle and entry (FR-11.6, FR-12.6), `403`
`password_change_required` (FR-4.5), `409` for `email_taken` and
`invitation_consumed`, `422` `odometer_decrease` and `last_admin`, `429`
rate-limited.

## 13. Observability

`middleware/logging.ts`: one structured line per request with request id,
method, path, status, duration, user id when present. A redaction list drops
passwords, tokens, cookies, and fuel-entry field values from any logged object
(NFR observability). No telemetry backend in M1.

## 14. Testing

| Layer | Tool | What |
|---|---|---|
| unit | vitest | units conversion, invariant helpers, error mapping, token and password helpers |
| repository | vitest + adapter harness | each repo method against Postgres and SQLite, including the INV-2 and INV-6 lock paths under `Promise.all` contention (AC-7, AC-8) |
| contract | vitest | drive `app.request()` for every route, assert the response validates against `openapi.yaml` (AC-10); run the whole file twice, once per adapter (AC-4) |
| journey | vitest + `@hono/node-server` | the AC-5 sequence over a real socket with a bearer credential; the AC-12 production-guard and `must_change_password` path; the AC-11 OIDC flow against the mock issuer |
| fixtures | `test/fixtures` | the nine named fixtures from `data-model.md`; a loader seeds either adapter |

Postgres in CI: a `services: postgres` container. SQLite: a temp file per test
file. The adapter harness parametrises every repository and contract test over
`['postgres', 'sqlite']`.

## 15. CI pipeline

One workflow, jobs map to the `specs/README.md` gates. All blocking.

1. `spec-lint` — Spectral on `openapi.yaml`.
2. `breaking-change` — `oasdiff` base vs head; fail on a breaking change with no
   version note.
3. `codegen-clean` — `pnpm openapi:write` then `git diff --exit-code`; also
   `drizzle-kit generate` then diff.
4. `schema-drift` — `drizzle-kit check`.
5. `typecheck` — `tsc --noEmit` across the workspace.
6. `contract` — the contract suite, matrix `[postgres, sqlite]`.
7. `test` — unit, repository, and journey suites, matrix `[postgres, sqlite]`.

`gitleaks` and the guarded lint/test from the existing `ci.yml` stay. All jobs
keep `permissions: contents: read` and use no secrets, so they run on fork PRs.

| `DATABASE_URL` | runtime connection, low-privilege role; scheme picks the adapter |

| `CORS_ALLOWED_ORIGINS` | browser origins, empty in an API-only deployment |

## 17. Risks

| Risk | Mitigation |
|---|---|
| Drizzle dual-dialect drift: a column helper behaves differently on SQLite | Every repository test runs on both adapters in CI from slice 1; no feature merges adapter-red |
| SQLite write serialization surprises under the INV-2 lock | `BEGIN IMMEDIATE` in the `UnitOfWork`; a contention test in the repository layer; SQLite is dev and test only so production uses Postgres row locks |
| OIDC library API churn (`openid-client` v6) | wrap it behind `auth/oidc/` so a swap is local; mock-issuer tests pin behaviour |
| `@hono/zod-openapi` cannot express a needed response shape | fall back to a hand-written schema fragment for that route; the codegen-clean gate still holds |
| Rate-limit memory store is per-process | acceptable for a single-process M1 deployment; R-1 decides the real target and a shared store then |
| Transactional email undecided (R-2) | interim: return links in the response; no code path depends on a provider |
| Secret storage undecided (R-3) | interim: env reference for the OIDC secret and session key; the schema already allows a stored encrypted value later |
| Scope creep from the SPA or CLI | both are out of this plan; `packages/` layout leaves room without a rewrite |

## 18. Build sequence

Each step ends green on the full pipeline. This feeds `tasks.md`.

1. **Workspace + skeleton.** pnpm workspace, `packages/api`, tsconfig strict,
   vitest, drizzle config, the CI jobs in section 15 wired but mostly no-op.
2. **DB foundation.** Schema for `deployment_settings`, `schema_meta`, `user`,
   `api_token`, `session`. Both adapters. `drizzle-kit` migrations.
   `UnitOfWork`. Repository tests on both adapters.
3. **Bootstrap.** `chotu bootstrap`: privilege probe, migrate, seed settings and
   first admin (all three credential paths), issue token. `CHOTU_ENV` guards.
   AC-1, AC-2, AC-12.
4. **Auth core.** Password sign-in, sessions, `must_change_password` gate, API
   tokens, sign-out. Rate-limit middleware. Error model. OpenAPI pipeline and
   the codegen-clean gate live from here.
5. **Users and admin.** Profile get/update, self-delete. Admin list, get,
   create, deactivate, reset, delete, grant/revoke, last-admin lock. Audit log.
   AC-7 (isolation baseline), AC-8, AC-9.
6. **Invitations and registration policy.** Invite create and accept, policy
   switch, `open` self-register with verification links.
7. **OIDC.** Provider CRUD, start and callback, link and unlink, auto-provision,
   mock issuer tests. AC-11.
8. **Vehicles.** CRUD, archive, delete guard, ownership `404`. Units module
   wired for `initial_odometer`.
9. **Fuel entries.** CRUD, list with date filter and cursor pagination, INV-2
   both-neighbour check under the vehicle lock, INV-3, INV-4, display
   projection. AC-3 path, AC-5 journey.
10. **Reconciliation and export.** Check registry, per-user and deployment runs,
    per-user export, admin backup export.
11. **Hardening pass.** Fill OpenAPI prose for LLM callers, finish fixtures,
    complete the contract suite, confirm every AC has a test, tune rate limits.
